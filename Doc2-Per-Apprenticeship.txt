1. GRADUATE PROFILE: WHAT COMPETENCE MEANS HERE
================================================================
A graduate works without a tutorial per mechanism. Concretely, and without
exception-by-omission, the graduate can: write idiomatic native .per; separate
facts, actions, goals, strategic numbers, timers, constants, engine state, and
world state in both reading and writing; recognize mature-AI control structures
on sight and state why each exists; distinguish language mechanism from
architectural convention; read large imperfect legacy code without losing the
thread in local syntax; reconstruct an unfamiliar AI's architecture from its
root and module graph; infer a module's role from its state and consumers;
name the initialization, maintenance, policy, execution, telemetry,
arbitration, and recovery layers in any competent bot; trace information from
observation to world effect across files; identify ownership and competing
writers; explain how production, economy, construction, military, technology,
scouting, and strategy subsystems interact; draw coherent module boundaries;
choose state representations with explicit lifecycles; compose independently
developed subsystems without letting shared state run uncontrolled; diagnose
failures that cross module boundaries; modify an established AI without
violating hidden assumptions; construct new subsystems from established
patterns; and reason about whole-bot behavior rather than single rules.
Syntax is the foundation. It is not the destination. Every chapter below
serves the profile above; anything that does not serve it was cut.

2. THE THREE KNOWLEDGES: LANGUAGE, IDIOM, ENGINEERING
================================================================
For every construct the course teaches three layers, and names which layer is
being taught, because conflating them is the root of most confident error.

Language knowledge: what the engine accepts. Operands, stores, parser
behavior, the command's literal effect. Example: (set-goal R V) writes the
constant V into goal R; it is Action-only. This layer comes from the registry
and the validator. It is necessary and nowhere near sufficient.

Idiomatic knowledge: how competent authors normally use the construct. The
recurring forms, naming, grouping, guarding, sequencing. Example: desire rules
raise train-* dials with c:max and never lower them; exactly one producer
family reads each dial. This layer comes from the corpus (Naga units.per,
Stock producers, Shadow pause/fire pairs). It tells you what "normal" looks
like, so abnormal stands out.

Engineering knowledge: why the pattern emerged — the engine limitation,
control requirement, performance pressure, or architectural need behind it;
when to use it and when not to; what assumptions it smuggles in; what breaks
when they fail. Example: dials exist because desire changes faster than
feasibility (threats spike in a pass; queues clear over minutes), so coupling
them directly would stampede production. This layer is the course's real
subject. A student who writes a rule has language. A student who reaches for
a dial, names its writer and reader, and can predict the failure when a second
writer appears, has engineering.

Each pattern entry in Chapters 4–7 follows the same spine: problem →
pressure → pattern → implementation → observed corpus usage → invariant →
failure mode → recovery → design tradeoff. Read that spine as a contract: if
you adopt the pattern, you adopt its invariant and its failure modes with it.

3. HOW TO WORK THIS COURSE
================================================================
Verification discipline: an unverified rule is a rumor. Every exercise ends
with an observation procedure (log line, count change, replay check) that
distinguishes working from believed-working. The instrumentation kit is fixed
throughout: chat-local-to-self as a local marker, up-chat-data-to-self with
%d and the prefix matched to the store (g: for goals, s: for SNs — mismatch
is the silent-wrong-value class of Document 1 §4), up-log-data under the
LOGSYSTEMS=AIScript VERBOSELOGGING CONSTANTLOGGING launch flags, one-minute
state dumps, and the package validator after every structural edit.

Evidence discipline: claims carry CONFIRMED / DIRECT / COMPOSED / INFERRED /
AEGIS-GENERALIZATION / UNCERTAIN exactly as in Document 1. A pattern observed
in Naga is an observed pattern, not an engine requirement; a pattern seen
independently in Stock, Naga, and Shadow is stronger; a pattern derivable
from engine semantics is stronger still. Recommendations without direct
observation are labeled engineering recommendations. Convention is never
presented as law.

Prose contract: precise technical exposition, causal explanations,
comparative analysis, counterexamples, failure analysis. No tutorial filler,
no motivational language, no "now let's try this" transitions, no jargon
without definition, no toy example presented as a mature system. Narrative
only where it clarifies, diagrams where they reveal structure, code where
code is the evidence, tables where relations outgrow prose.

4. PATTERN LANGUAGE I: TIME AND STATE
================================================================
4.1 One-shot initialization. Problem: boot state (timers, SN defaults, mode
goals) must be established exactly once. Pressure: per-pass re-execution
would reset tuning and re-fire enables. Pattern: (true) => (...,
(disable-self)). Corpus: ~370 one-shot inits in Stock (boot at AI (HD
version).per:5040–5132 enabling civ-explore/attack/spread-military timers and
SN defaults); ~199 in Shadow (defense-state zeroing at Shadow DC7.per:
1957–1978). Invariant: one-shots run before first maintenance use; nothing
downstream may assume they re-run. Failure: a maintenance rule depending on
re-initialization rots after first pass. Tradeoff: disable-self takes effect
next pass and disabled rules still count for jump deltas (registry) —
one-shots inside jump regions shift landings; freeze tuned regions.

4.2 Heartbeat/timer loops. Problem: periodic reassessment without per-pass
cost. Pressure: 60-second strategy cadence vs per-pass evaluation budget.
Pattern: enable once at boot, gate rules on (timer-triggered T), re-arm in
the firing rule (self-perpetuating) or by a dedicated re-arm rule testing
(up-timer-status T != timer-running) as Shadow does for ONE-MINUTE/30SEC/
TWO-MINUTE/THREE-MINUTE (Shadow DC7.per:22541–22576); Naga enables seven
timers at boot including one-minute=7 for 60s (initialization.per:505–517).
Invariant: every heartbeat names its re-armer. Failure: missing re-arm
degrades a heartbeat to a one-shot — silent, and the classic mystery ("it
worked once, then never again"). Recovery: audit enable sites per timer id;
Stock's attack-timer re-arm at multiple sites (e.g. 150s naval commit,
60s retreat hold, 3s reset probe) shows intentional multi-rate use of one id.

4.3 State latching (SEEN→CURRENT→STALE→EXPIRED). Problem: volatile inputs
(Naga zeroes threat SNs every pass, threats.per:412–431) make absence of
sighting indistinguishable from absence of threat. Pressure: LOS flicker
would become production flicker. Pattern: on SN>0 copy to goal plus
game-time stamp (up-get-fact game-time 0 seen-X); retain while fresh;
release after silence threshold. Invariant: latch values must equal the SN
at sighting time — verify with the s:/g: prefix check (Document 1 §4
incident: g:max on an sn-* name reads the unrelated goal cell). Failure:
latched garbage poisons every downstream layer while compiling clean.
Recovery: expiry rules per class; standing minima (Chapter 6) survive expiry.

4.4 Hysteresis. Problem: single-threshold guards flap (enter/exit same
boundary under noise). Pressure: superiority oscillates 0/1 at contact.
Pattern: enter low, exit high (enter hold at sup<1, release at sup≥2;
enter harassed at ≥2 enemies in town, exit at 0). Invariant: the gap exceeds
observed noise amplitude. Failure: coincident thresholds produce
attack/retreat oscillation indistinguishable from authority bugs — check
thresholds before redesigning authority.

4.5 Cooldowns and delayed transitions. Problem: re-entry must wait out
transients (retreat dust, queue drain). Pattern: enable-timer on exit,
guard re-entry on (up-timer-status T != timer-running). Stock: retreat holds
attack-timer 60 then re-probes at 3s after reset clears (34440–34450 →
34583–34596). Invariant: cooldown length covers the transient it guards.
Failure: too short = re-entry into the same emergency; too long = passivity
misread as strategic patience.

4.6 Interruption and resumption (re-entry). Problem: durable activities
(attack, save-up, tech pause) meet emergencies mid-course. Pattern: pause
execution, preserve authorization, resume with re-checked guards — never
resume a stale order. Shadow's pause enum (pause ≠ −1 suspends, −1 resumes,
§7.1 corpus) and the retreat-coherence shape (groups-zero + retreat orders
while attack authorization stays set) are the two canonical forms.
Invariant: resume re-evaluates guards. Failure: canceling authorization
instead of pausing forces full stand-down plus slow re-authorization (the
passivity ratchet); resuming obsolete objectives feeds units into lost
fights. Recovery: edge latches + timer-paced refire.

================================================================
5. PATTERN LANGUAGE II: CONTROL FLOW
================================================================
5.1 Guard-skip (forward jump). Problem: deep eval blocks cost passes when
irrelevant. Pattern: test cheap absence, (up-jump-rule N) over the block.
Corpus: Shadow skips 44/56/12-rule targeting blocks when RangedGroup is
empty (2057–2064, 2536–2540, 2666–2671); Naga threat filter skips 3
(threats.per:8–18); Stock skips 2 without siege infrastructure
(5321–5326). Invariant: the skipped region's preconditions are exactly the
negation of the guard. Failure: insertions between jumper and target
silently retarget — freeze tuned regions; never jump across #load-if
regions (registry warning verbatim for up-jump-rule and up-jump-dynamic).

5.2 Search loops (negative jump). Problem: iterate a found set within one
pass. Pattern: index goal + (up-jump-rule -N) back to the scan head, as in
Shadow's search-state loop (9805–9811) and Naga's ally scan over players
1–8 (interaction.per:2286–2290, jump −2 with focus increment). Invariant:
monotonic progress toward a bound (index < 8) or the loop is infinite and
the pass never ends — a genuine freeze class. Failure/recovery: always bound
loops by counts; test with empty sets (zero iterations must fall through).

5.3 Computed dispatch. Problem: one entry point, many behaviors, no
subroutines in the language. Pattern: bookmark + jump-direct. Naga's
affinity dispatcher (strategies.per:1–10): if affinity-function-id < 10000
skip the 136-rule table, else record (up-get-rule-id) and jump 135 to the
return; callers set candidates, invoke via up-jump-direct, diff
current-affinity before/after (initialization.per:6857–6890). Invariant:
table length frozen; bookmark protocol documented at call sites. Failure:
table edits without delta updates misroute every dispatch. This is the
closest native .per comes to a calling convention — recognize it on sight.

5.4 Preprocessor specialization. Problem: one codebase, many maps/modes.
Pattern: #load-if-defined blocks selecting constants and rule variants
(Shadow TINY-MAP scout HP at 322–328; pocket/flank scouting at 435–443;
Naga's 4-deep map exclusion nest at buildings.per:232–235 with #else on the
outermost). Invariant: every #load-if has its #end-if in the same file and
jump regions avoid conditional spans. Failure: duplicate-preprocessor-else,
nesting-depth violations (validator codes exist because authors hit them).

================================================================
6. PATTERN LANGUAGE III: PRODUCTION AND RESOURCES
================================================================
6.1 Demand/executor separation via dials. Problem: desire changes faster
than feasibility (threats spike per pass; queues clear over minutes).
Pattern: desire rules raise goal ceilings with c:max/g:max and never lower
them; producer rules test (count g:< dial) + feasibility guards
(up-can-train/can-train) then issue (train/up-train). Corpus: Naga
mangonel — writer at units.per:1336–1351 ((up-modify-goal train-mangonel
c:max 2) under tower/ranged pressure with age/superiority guards), readers
at units.per:11323–11329 (count g:< dial + not-targeting + enough-siege +
up-can-train → train), escrow spend decrements the dial
(escrow.per:635–640). Stock's contrasting choice: direct (can-train X) =>
(train X) with long enemy-state guards (villager at 19399–19407, spearman
at 28117–28131) — no dial layer, steeper guards instead. Invariant: dials
are raised-only by policy families and read-only by producers; any lowering
needs an owner (expiry rule). Failure: second writer lowering = ownership
fight; dial without reader = desire without executor; escrow spend without
decrement = dial stuck high. Tradeoff: dials add a frame of latency and a
naming/ownership burden in exchange for decoupling fast desire from slow
feasibility — worth it past a handful of producers.

6.2 Producer/consumer chains (construction). Same separation for buildings:
Naga writes construct-mill ceilings (buildings.per:3071–3075) and executes
via placement data + sn tuning + (up-build place-control 0 c:
food-placement-camp) with (disable-self) + jump past the chain
(3076–3094); helpers in buildingsFunctions.per read the same dials
(g:max). Invariant: placement/affordability/queue checks stay with the
executor, never the desire rule. Failure: desire rules issuing builds
directly bypass queue discipline and double-place.

6.3 Reservation and escrow. Problem: lump sums (ages, techs, TCs) must
survive contact with per-pass spenders. Pattern: divert income
(set-escrow-percentage), accumulate (up-modify-escrow c:max N under a pause
id), fire on escrow-aware feasibility (can-research-with-escrow), release
and clear. Corpus: Shadow pause/fire pairs (Scale Mail at 14309–14324;
Castle via escrow with CUP gate at 14893–14905); Stock TC save/spend
(escrow-purpose-goal town-center at 5687–5717) and Imperial at 18282–18293.
Shadow additionally mirrors physical escrow into goals and reasons on NET =
gross − escrowed (1821–1845). Invariant: every escrowed resource has a
named purpose and a release path; gross-amount checks are blind to escrow
(use with-escrow facts or NET goals). Failure: un-released escrow starves
normal commands (train cannot see escrowed stock); pause never cleared
(−1 discipline); trash rules eating savings for lack of escrow guards.
Registry: research without can-research guards risks "possible crashes" —
guard every research/train rule.

6.4 Priority arbitration under scarcity. Problem: independent lines each
authorize past what the economy sustains. Pattern: sum-of-deficits vs a
ceiling from existing funding bands, enforced in fixed cost order on
non-mandatory lines only; mandatory counters immune. Invariant: arbitration
reads final (post-suppression) deficits and never touches believed-threat
lines. Failure: ceiling computed pre-suppression (double counting);
blocked-by-infrastructure demand consuming ceiling (subtract flagged lines
first — stable/castle/monastery/workshop absence marks unfillable demand).

6.5 Deficit correction and watchdogs. Problem: open-loop requests rot
(queues stall, placements fail). Pattern: deficit = max(desire) − current
floored at 0, recomputed per tick; persistence beyond N ticks logs UNMET
and switches producer or flags infrastructure gap. Stock's reset probe
(attack-timer 3 after reset clears) is the same shape at military scope.
Invariant: completion observed in world state, never inferred from
issuance. Failure: retrying a structurally blocked producer forever.

7. PATTERN LANGUAGE IV: OBSERVATION TO EFFECT
================================================================
7.1 Census/aggregation. Problem: decisions need counts, engine gives
objects. Pattern: zero accumulators per pass, per-line focus queries,
roll-ups. Naga threats.per:412–431 zeroing; camel/knight lines into
sn-camels/sn-cavalry via up-get-focus-fact + up-modify-sn g:+ temporary-goal
(463–489); roll-ups sn-ranged s:+ sn-archers/skirms, sn-monksiege s:+
sn-monks/siege (1085–1094). Shadow: up-get-threat-data into gl-threat-*
plus villager snapshot (17119–17127), guarded by a 14-rule skip when stale
(17401–17408). Invariant: census precedes policy in source order every
pass; accumulators never persist. Failure: reading accumulators as memory
(the LOS-loss→zero oscillation); policy placed before census reads last
pass's world.

7.2 Classification pipelines. Threat lines → classes (cav/arch/inf/siege/
monk) → per-class requirement. Naga's sn-ranged folding (archers + skirms
+ gunpowder + cavalry-archers) shows classification is a judgment (what
counts as "ranged mass"), not a measurement. Invariant: the folding rule
is documented where the class is consumed, or the next author refolds
differently and double-counts.

7.3 Policy-to-dial translation. Joint requirement = max(belief, standing,
dial): beliefs release on expiry, standing minima persist (counter-fulfilled
≠ army-fulfilled), dials carry strategy intent. Funding gates suppress only
discretionary top-up, never mandatory counters. Invariant: suppression
rules run after joint computation and before arbitration reads deficits.

7.4 Authorization and attack state machines. Two valid authorities: engine
attack-groups via the attacking bit + group counts (Naga: start bands at
militaryMacro.per:730–745, assisted bar 746–757, retreat converse 759–774),
or UP-group micro with groups zeroed and town-size uncapped (Shadow:
gl-attacking + 1000 + TSA at 16638–16651, symmetric retract at
16653–16667). Stock: attack-goal 0/1/6 staging with attack-timer pacing and
attack-now commit (36340–36358), retreat-now-goal + reset discipline for
recovery (34440–34450 → 34583–34596). Invariant: exactly one authority
owns start/stop per force; deny precedes force in file order with timer
guards. Failure: dual authorities without precedence oscillate; canceling
authorization on retreat causes stand-down + slow re-auth.

7.5 Verification and reassessment. Every chain ends in world observation:
counts changed, building exists, superiority recomputed, gap reassessed.
Shadow's town-safe latch (17725–17749) and Stock's reset probe are
verification gates before resuming offense. Invariant: no chain is closed
by issuance. Failure: assumed completion (the "requested ≠ committed ≠
executed" collapse of Document 1).

8. MODULARITY: WHY COMPETENT BOTS ARE MODULAR
================================================================
Modularity answers cognitive complexity, reuse, separation of concerns,
initialization dependencies, state ownership, source-order management,
maintainability, debugging, experimental replacement, domain specialization,
policy/mechanism separation, control-flow containment, multi-author
evolution. Naga's 22-module tree (initialization, threats, trade,
militaryMacro/Micro, escrow, technologies, interaction, buildings,
builders, units, gatherers…) lets an engineer open one domain without
loading the whole bot into working memory; Stock's 38,217-line monolith
pays for global searchability with merge fragility; Shadow's 22,603-line
monolith with enum discipline sits between.

The subtle point, drilled until reflexive: a module boundary is a
source-organization boundary, NOT a state-isolation boundary. Files stay
coupled through goals (train-*/construct-*/assistance/attacking), SNs
(threat slots, superiority), timers (one-minute, retreat-timer),
engine/queue state, and source-order assumptions (census before policy,
deny before force, inner loads mid-file at initialization.per:634–635/6773
and gatherers.per:3730). File separation does not imply behavioral
independence. Consequences the course rehearses: moving one rule can
retarget jumps pages away; adding a writer to a foreign dial breaks a
distant producer; loading a module without its initializer's timers
silently converts heartbeats to dead rules. Modularity contains reading
and writing; only ownership discipline contains behavior.

 10. STYLE AS ENGINEERING EVIDENCE
================================================================
Naming: Naga's train-*/construct-* verbs mark dial layer membership on
sight; Stock's *-goal terse ids (attack-goal 2, strategy-goal 3,
retreat-now-goal 20 with value-meanings in trailing comments) mark a
central-enum style; Shadow's gl- prefix + UPPER state tokens
(gl-attacking YES/NO, FIRING/MARCHING/DEFENDING) mark file-scoped state
machine membership. Prefixes (gl-, sn-, bwc-) are namespace claims — read
them as ownership declarations and verify by writer search.

Grouping: rule families separated by banner comments and blank lines are
subsystem claims; verify by shared state (common dial/goal = one
subsystem regardless of banners). Section ordering (constants → init →
census → policy → executors → recovery) is a dataflow claim; violations
(policy before census) are suspects, not style choices.

Repetition: near-duplicate producer guards (Stock's spearman/knight/villager
families) signal missing abstraction OR deliberate per-case tuning — check
whether the differing conjuncts encode real distinctions (focus-player
counts, age gates) before "cleaning up". Commented-out alternatives (Stock's
349 disabled chat- lines; Naga's DISABLED patrol rule) are decision fossils:
they record rejected tunings, and re-enabling them replays old bugs.

Defensive checks (pending-objects, queue-idle, can-* guards, blocked
flags) mark executor maturity; their absence marks either boot code (safe)
or hazard (unsafe). Indentation/tab discipline and closers ("end init; end
jump") mark jump-region awareness. Style is the author's architecture
diagram drawn in Kraft durch Verhalten — learn to read it before redrawing.

 11. WHAT THE 2296-SYMBOL CORPUS ACTUALLY CONTAINS (MINED, NOT SAMPLED)
================================================================
Every file under generated/symbols was parsed programmatically. Exact
results (counts computed, not estimated):

Kinds [DIRECT: computed over all 2296 files]: value 1175, object 356,
command 347, tech 247, strategic-number 171 (total 2296). Only Kind==command files carry a Syntax: line (347 = 347).
The 171 sn-* files and all value/object/tech files are syntax-less
reference rows — the registry documents vocabulary, not behavior, for most
of the language surface. Pedagogical consequence: command lookup answers
arity; it almost never answers semantics. Semantics live in corpus usage.

Detail fields: 918 distinct values, 795 singletons (per-ID rows: SN n,
Object n, Tech n, ResourceType 272, MapType 193, Terrain 116, Civ 60,
FactId 57). Only 123 Details repeat. The repeating set IS the engineering
core: Fact/Action duals, Can-Do facts, attack/economy actions, DUC search
actions, timers, goals, chat. Students should learn the repeating 123
before the singleton 795 — frequency in the registry mirrors frequency in
real rule tables.

Dual-nature commands (Detail contains "Fact/Action") [DIRECT: computed over
all 2296 files]: exactly 21 —
up-modify-goal, up-modify-sn, all up-get-*-fact variants (get/get-focus/
get-player/get-target/get-fact-max/min/sum), up-get-object-data(-target),
up-get-point-contains, up-set-target-by-id, up-set-target-object, the
up-find-* family (local/remote/resource/status), up-add-object-by-id, and
xs-script-call. Architectural meaning: these 21 are the bridges — they read
engine state into script state (facts→goals) or test-and-touch in either
position, which is why Naga legally embeds up-set-target-object in
condition position (militaryMicro.per:63–74). Misreading a bridge as
action-only produces the "moved it to actions and broke the guard" mystery.

Command families by filename: up-* 189 (all commands), sn-* 171, build-* 58,
attack/group 94, search/target super-family (find/target/filter/search/
remove/group) 129, chat/taunt 26, train-* 15, research-* 24, escrow-* 11,
timer-* 11, goal-* 12. The 129-strong search/target family is the DUC
micro substrate most beginners never meet and most advanced bots live in.

State writers vs executors (judgment-filtered): writers — set-goal,
set-strategic-number, up-modify-goal/sn, up-get-fact family, timers,
escrow splits, set-shared-goal, set-signal, generate-random-number;
executors — train/up-train, build/up-build(-line), research/up-research,
attack-now, up-target-objects/point, delete-*, tribute, buy/sell, resign.
The writers list is short and closed; the executors list is short and
closed [COMPOSED: judgment-filtered from keyword hits over command
descriptions, cross-checked against Naga/Shadow producer rules].
Everything else — 200+ commands — is observation, search,
guarding, or messaging. Pattern recognition starts here: in any unfamiliar
file, find the writers first (they define the state), then the executors
(they define the effects); the rest is plumbing.

Guard-requirement signals (description mining): "must" 295 lines,
"guard" 78, "prevent" 19, "ensure" 13, "never" 16, "crash" 2. Strongest
verbatim warnings a graduate memorizes: research — "use can-research [or]
escrow [variants] in any rule where you use the research command, in order
to prevent possible crashes"; up-train-site-ready — "Unit lines, negative
unit IDs, or invalid unit Ids may result in a crash" + "Do not use unit
lines or unit classes"; up-jump-rule/dynamic — "Never use this command
where #load-if blocks may make your jump target unreliable" (twice);
up-modify-group-flag — manage flags carefully, never store foreign-owned
objects; sn-target-point-adjustment — restore to 0–5 or up-target-point
"sends units to the left corner of the map". Each warning is a mystery in
Chapter 15 waiting to happen; each maps to a debugging-taxonomy class.

Store-crossing commands (descriptions naming both goal and strategic
number): exactly 10, including up-compare-sn (whose syntax takes a GoalId
despite the name), up-modify-goal, set-goal, strategic-number. These ten
are where prefix discipline (Document 1 §4) is load-bearing — and where
the g:max-on-sn-* incident lived.

Timer infrastructure: 11 symbols — enable/disable-timer, up-set/get-timer,
up-timer-status, timer-status/disabled/running/triggered states, plus
object-data-attack-timer. Note up-get-timer and up-set-timer exist: timers
are readable into goals and settable dynamically, enabling computed
cooldowns, not just constants.

Oddities: zero empty/malformed files; 19 pure-numeric basenames (-1,
-266…-399: sentinel values like "use -1 to ignore the ActionId"); the word
"excepto" appears nowhere. The corpus is clean reference data with thin
behavioral prose — corroborate every behavioral claim against running code.

================================================================
 12. STATE AS A SYSTEM: LIFECYCLES, OWNERSHIP, INVALIDATION
================================================================
Stop seeing variables; see lifecycles: initialization → writer → mutation →
reader → effect → observation → mutation → reset/expiry/release. For every
state object that matters, the engineer answers: who initializes it (boot
rule or first-writer default — goals start at 0, which IS a design fact);
who writes it (exactly one family, or an arbiter); who reads it (executors,
guards, telemetry); who can overwrite it (competitors, search yours for);
what the value means (units documented at the defconst, like Stock's
retreat-now-goal 1/2/3 conditions); when it goes stale (threat beliefs on
LOS loss; superiority on army death; escrow mirrors on un-released
spends); what invalidates it (age change, emergency, blocked
infrastructure); what resets it (expiry, release, re-entry guard); what
happens if the consumer never acts (UNMET persistence → watchdog); what
happens under incompatible demands (arbitration, Chapter 6.4); what happens
after interruption and on re-entry (resume re-checks guards).

Ownership assignment is the design act: single writer per goal; many
writers only through max-semantics dials or an explicit arbiter rule;
timers owned by their re-armer; escrow splits owned by the purpose goal
(Stock's escrow-purpose-goal pattern); search sets owned per pass (reset
before fill — up-full-reset-search discipline). Invalidation is the
forgotten half: every latch needs its expiry, every pause its −1, every
escrow its release, every loop its bound. Audit any subsystem by walking
its states through the lifecycle questions; unanswered ones are bugs with
the serial numbers filed off.

================================================================
 13. POLICY VERSUS MECHANISM
================================================================
What should happen versus how the engine makes it happen. Full chain:
observation → interpretation → requirement → policy → demand →
authorization → feasibility → execution → completion → recovery. Small bots
compress layers (a guard tests enemy count and trains directly, as Stock's
spearman rule does); large bots separate them (Naga's threat→dial→producer
chain; Shadow's pause→escrow→fire chain). Separation pays off as complexity
grows because each layer changes for different reasons: observations change
with scouting, policy with strategy, feasibility with economy, execution
with engine version. Compressed layers force synchronized edits across
unrelated reasons — the "trivial edit breaks distant behavior" phenomenon
is usually a compressed layer snapping.

Exercise (recurring): take any Stock producer and reconstruct its hidden
layers — name the capability it answers, the requirement it implies, the
authorization it assumes, the feasibility it checks, the completion it
ignores. Then take the Naga mangonel chain and point at each layer's
physical rule. The layers are present in both; only their explicitness
differs. Design judgment = choosing per-subsystem how explicit each layer
earns the right to be.

================================================================
 14. THE FAILURE OF LOCAL REASONING (ELEVEN CASES)
================================================================
A rule can be locally correct and globally wrong. Eleven canonical forms,
each with mechanism and detector:
1. Correct writer, wrong owner — value right, author unauthorized; detector:
writer search shows two families. 2. Correct command, wrong timing —
escrowed savings spent by a per-pass producer before the age rule fires;
detector: savings curve flattens. 3. Correct condition, stale state —
threat latch never expired; detector: belief persists with SN at zero.
4. Correct demand, competing writer — dial raised then lowered by a foreign
rule; detector: dial flicker. 5. Correct timer, incorrect re-arm —
heartbeat degraded to one-shot; detector: fired-once-then-silent. 6.
Correct jump, invalidated target — insertion shifted landing; detector:
behavior changed with no local edit (diff the jump region). 7. Correct
module, wrong load order — inner load reads uninitialized timers/dials;
detector: works when merged, fails modular (order suspect). 8. Correct
executor, missing authorization — producer fires outside policy windows;
detector: right units, wrong battles. 9. Correct policy, no feasibility —
gold-gated Cataphract demand with empty coffers; detector: deficit
persists, queue empty. 10. Correct command, assumed completion — train
issued into a blocked queue; detector: UNMET watchdog. 11. Correct
transition, no recovery path — dead state entered legally; detector:
minute-log flatlines in a non-terminal state. The theme is one sentence:
correctness is a property of the rule-in-system, never of the rule alone.

================================================================
 15. ENGINEERING MYSTERIES (FORENSIC PUZZLES)
================================================================
Each mystery states symptoms, withholds the mechanism, and resolves into a
durable lesson. Work them before reading the resolutions.

M1. The bot affords the unit; the production rule fires; the unit never
appears. (Resolution: escrow holds the food — gross checks pass,
train cannot spend escrowed stock; the with-escrow variant or a release
was missing. Lesson: affordability has two accountings.)

M2. The code compiles; a number changes; behavior is irrational; nothing
crashes. (Resolution [CONFIRMED: validator-definite finding plus forensic
fix]: g:max on an sn-* name reads the unrelated goal
cell — the store confusion of Document 1 §4. Lesson:
prefixes are the type system; audit g: operands mechanically.)

M3. One rule moved; condition and action identical; behavior differs.
(Resolution: source order — a jump landing shifted, or a competing writer
now runs last. Lesson: position is semantics for jumps and writers.)

M4. Two modules correct in isolation; together they oscillate.
(Resolution: competing writers on one goal, or dual attack authorities
without precedence. Lesson: compose through ownership and precedence,
never through timing.)

M5. Correct state entered, never left. (Resolution: latched without exit —
missing expiry, un-released escrow, pause never cleared. Lesson: every
latch ships with its release.)

M6. Worked once, then never again. (Resolution: heartbeat missing re-arm,
or one-shot consumed. Lesson: name every timer's re-armer.)

M7. Research ordered; game stutters; occasionally dies. (Resolution:
unguarded research — the registry's documented crash link. Lesson: guard
every research/train rule; feasibility guards are safety equipment.)

M8. Micro orders send armies to the map corner. (Resolution:
sn-target-point-adjustment left outside 0–5 — registry verbatim. Lesson:
global modes are shared state; set-use-restore discipline for SN modes.)

M9. Ally-coordinated attacks never trigger. (Resolution: assistance loop
never matches — focus-player scan or taunt acknowledgement missing.
Lesson: cross-player facts (up-allied-goal) need the full handshake:
scan, stance, shared target, ack.)

M10. Threat response works in testing, vanishes in real games.
(Resolution: policy placed before census in source order reads last
pass's world — one frame stale, fatal at contact. Lesson: order the pass:
zero → census → roll-up → policy → executors.)

M11. Refactor for clarity; behavior degrades everywhere slightly.
(Resolution: "clarity" destroyed jump regions, enum groupings, and guard
order the tuner depended on — the load-bearing ugliness of Chapter 17.
Lesson: ask what invariant the ugly code protects before cleaning it.)

================================================================
 16. FORENSIC READING PROGRESSION: TEN PHASES ON UNFAMILIAR CODE
================================================================
Take an AI you did not write (Naga first, then Stock, then anything) and
work the phases in order, writing down each answer before proceeding. Each
phase has an exit criterion; a phase skipped is a phase that will ambush
you later.

Phase 1 — Package: root, loads, non-loads. Exit: the full load graph on
one page, including inner loads (Naga's initialization.per:634–635/6773,
gatherers.per:3730) and the debug tail. Note what does NOT load — dead
files are suspects, not scenery.

Phase 2 — Architecture: modules and apparent responsibilities from names,
sizes, and rule density. Exit: one-line role hypothesis per module (to be
confirmed or killed in later phases, never assumed).

Phase 3 — State: the goals, SNs, timers, constants that matter. Method:
collect defconsts, then rank by writer-count and reader-count (writers
first, per Chapter 11). Exit: the top-20 state inventory with id numbers.

Phase 4 — Dataflow: who writes what, who reads it. Build the writer→state
→reader table for the top 20. Flag multi-writer cells immediately — each
is either max-semantics, an arbiter, or a bug. Exit: no multi-writer cell
left unclassified.

Phase 5 — Control: state machines (goals with small id sets + transition
rules), loops (negative jumps with bounds), heartbeats (re-armed timers),
dispatch (jump-direct + bookmarks). Exit: every loop bounded, every machine
drawn with exits checked (dead-state audit).

Phase 6 — Authority: who decides each important thing (attack, age-up,
tech, production mix). Exit: one named authority per decision plus its
preconditions; dual authorities flagged with precedence evidence.

Phase 7 — Execution: which rules actually issue engine commands (the
executor list of Chapter 11 is short — find them all). Exit: every train/
build/research/order traced back to its feasibility guard; unguarded ones
listed as hazards.

Phase 8 — Recovery: what happens when actions cannot occur (UNMET paths,
resets, fallbacks, blocked flags). Exit: named recovery for every major
chain, or an explicit gap ("no recovery observed for X").

Phase 9 — Hypothesis: what the engineer believes each subsystem intends.
Written as falsifiable sentences ("this family holds 2–3 monks for healing
independent of siege belief"), never as restatements of code.

Phase 10 — Verification: the observation that would prove or kill each
hypothesis (log line, replay check, experiment from Document 1 Chapter 12).
Exit: at least one killed hypothesis per subsystem studied — a reading with
no kills was skimming.

Graduate drill: perform all ten on Stock's escrow-purpose-goal chain
(5687–5717, 18269–18293) and on Naga's affinity dispatch (strategies.per:
1–10 + initialization.per:6857–6890), then compare the two write-ups.
Same phases, different architectures, different answers — that variance is
the lesson.

================================================================
 17. HISTORICAL HUMILITY: WHY UGLY CODE MAY BE LOAD-BEARING
================================================================
Repetition, odd orderings, magic numbers, commented-out alternatives, and
defensive checks that look paranoid usually predate you and protect
something [INFERRED general rule from DIRECT instances: Stock's 349
disabled chat lines, Naga's parked patrol rule, Shadow's turn counter]. Candidate reasons, in check order: engine semantics (dual-nature
commands in conditions); parser limitations (no labels, so positional jumps
with frozen regions); missing abstraction (the language has no functions —
repetition IS the subroutine); source-order dependence (census before
policy; deny before force); jump addressing (deltas count disabled rules);
performance (guard-skips bought passes); compatibility (UP vs DE duals,
age-gated idioms); defensive behavior (pending/queue/idle checks earned by
past stalls); legacy behavior (obsolete-SN reuse like sn-infantry-threat
53); incremental evolution (rejected tunings fossilized as comments);
constraints from another subsystem (a weird guard satisfying a distant
executor). The rule is procedural: ask what invariant the ugly code might
protect, find the failure its removal would cause, and only then decide.
Stock's 349 disabled chat lines are not clutter but a tuning log; Naga's
DISABLED patrol rule is a parked experiment; Shadow's turn counter is a
timer system built from arithmetic because timers were all spoken for.
Refactoring without the invariant inventory is how M11 happens.

 18. BOT THREADS: FLUENCY, SYSTEMS, ENGINEERING (PRACTICE SPINE)
================================================================
The three bots remain, reinterpreted as practice volume for the pattern
language — not as the curriculum's content, which is Chapters 4–17.

Bot 1 — Language fluency. Build LittleBot file by file: package, first
rule, facts, goals, prefixes, timers, first production with guards. Each
step verified by observation; five deliberate failures classified by the
twelve-class taxonomy (parser/symbol/load/semantic/scheduling/state/
authority/resource/execution/completion/recovery/version). New load-bearing
addition: split Bot 1 into two files with a (load ...) and break it three
ways (missing target, wrong order vs defconst use, duplicate load) —
loading is practiced, not described. Exit: syntactic and semantic fluency;
the twelve classes are reflexes.

Bot 2 — Systems thinking. State machines with drawn graphs and audited
exits; hysteresis on every threshold pair; cooldowns with named re-armers;
interruption preserving authorization with guard re-check on resume;
ownership with one arbiter built by hand; the production dial end to end
(verified Naga mangonel shape: desire ceiling → count-vs-dial → feasibility
→ train → escrow decrement); deficit watchdog diagnosing a deliberately
blocked queue. Exit: thinking in interacting systems; every exercise
names writers, readers, and the invariant.

Bot 3 — Engineering on real structures. Reconstruct one unfamiliar module
per week using the ten phases; compare Stock-direct vs Naga-dial
production on the same unit and state the tradeoff from evidence;
implement the observe→verify chain one arrow at a time with per-arrow

provoke oscillation by removing precedence, then restore it and keep the
log as a regression test. Exit: independent subsystem design inside
existing architecture, traced observation to effect.

================================================================
 19. DESIGNING FROM A BLANK PROJECT
================================================================
No universal template — a reasoning process: requirements (what must the
bot do on which maps, against whom) → domain decomposition (economy,
production, construction, tech, military, strategy, scouting, recovery —
merge or split by expected interaction density) → state inventory (every
goal/SN/timer the design needs, with lifecycle answers from Chapter 12
before any rule exists) → ownership assignment (one writer per cell;
arbiters explicit) → observation layer (census shapes, cadences) → policy
layer (requirements as max-semantics joints) → execution layer (dials,
guards, executors) → recovery layer (deficits, watchdogs, fallbacks) →
module boundaries (drawn around ownership, not aesthetics) → load order
(constants → init → census → policy → executors → recovery; inner loads
documented) → verification strategy (per-arrow observations + validator +
replay). Architectural options with honest tradeoffs [engineering recommendations:
not directly observed as advice, derived from the atlas above]: centralized
controller (Stock-like: one table, fast global reasoning, merge pain);
distributed dials (Naga-like: decoupled tempo, contract burden);
libraries + thin controllers (helpers owned once, policy files small);
telemetry module from day one (minute state dumps are cheaper than
archaeology); state-machine controllers for strategy modes. Choose per
subsystem, document why, revisit when the reason changes.

 21. INTUITION DRILLS: SEE-THIS—ASK-THAT
================================================================
(timer ...) → what periodic process, who re-arms. Multi-writer goal →
ownership suspect; find the arbiter or file the bug. Production dial →
writer, consumer, lowering rule (if any). disable-self → one-shot; check
it sits outside jump regions. Repeated census rules → aggregation; check
zeroing and order vs policy. Threshold pair → hysteresis gap vs noise.
Command → is completion observable, and where. Module load → what state
was assumed initialized. Jump → positional fragility; frozen region?
Large rule pile → partition into subsystems by shared state. Escrow
percentages → named purpose + release path. Commented-out code → decision
fossil; read before re-enabling. Drill weekly on unfamiliar files until
the questions precede conscious effort — that precedence is the intuition.

================================================================
 22. GRADUATION: INDEPENDENT ENGINEERING INSIDE AN UNFAMILIAR AI
================================================================
Receive an unfamiliar AI and a new requirement (e.g., answer cavalry with
a production path the bot lacks). Without scaffolding: (1) reconstruct the
architecture (ten phases, written); (2) identify relevant modules;
(3) inventory existing state; (4) map writers/readers; (5) determine
ownership; (6) select established patterns with corpus citations;
(7) decide extend-vs-new-module with reasons; (8) design the state model
with lifecycles; (9) define the module boundary; (10) implement; (11)
integrate preserving existing behavior (before/after replay + validator);
(12) introduce a controlled failure and diagnose it blind; (13) verify
runtime effects per arrow; (14) demonstrate recovery (blocked producer,
stale belief, interrupted execution); (15) explain the resulting
architecture aloud in design vocabulary; (16) document evidence and
uncertainty per claim. Passing is not a working bot — it is a traced,
owned, verified, recoverable subsystem inside a living ecosystem, plus an
engineer who can narrate every decision twice: once from evidence, once
from tradeoffs.

================================================================
 23. FINAL STANDARD
================================================================
(defrule ...) first reads as "what does this syntax mean", then "what
mechanism is this rule in", then "what subsystem owns it", and finally
"what contract does this subsystem implement, what state does it consume
and produce, what can interfere, and what world-state evidence would prove
it works". The graduate opens Naga, Stock, or any unfamiliar competent AI
and reads an engineered system: modules with purposes, idioms with
reasons, organization with pressures, strength with boundaries, danger
with names — and then builds something new from the same reasoning.
Document 1 establishes what the machine is. This document taught how its
engineers think. The rest is practice volume.
