0. How this course works (read first)
* You need no AoE2 AI knowledge. General programming helps but every .per concept is introduced from zero.
* Each lesson follows the same ten steps (what / why / engine behavior / smallest example / verification / failures / causes / professional debugging / connection / next). Do not skip verification steps - an unverified rule is a rumor.
* Language rule for this course: no "obviously", "simply", "just", "as you know", or "easily" where reasoning is owed. If a step feels skipped, that is a course bug - note it and work it out explicitly.
* You will build three bots: Little (language + execution model), Thinking (state over time), Adaptive (observe→verify loop). Then a fourth, alone.
* Keep Document 1 beside you. Margin tags like [Doc1 §5.3] point at the engineering contract behind each lesson.
* Debugging taxonomy (used from Lesson 1): parser / symbol / load / semantic / scheduling / state / authority / resource / execution / completion / recovery / version. Every failure you meet gets classified - that classification is the skill.
BOT 1 - THE LITTLE BOT (language + execution model)
Goal for Bot 1: "I want the AI to do one thing when one condition is true. How do I express what the engine can observe, write the condition, issue the action, load the code, and prove it happened?" [Doc1 §§2-5]
Lesson 1.1 - Files: where the AI lives
What is this? An AI is a named package: a marker file (<name>.ai, zero bytes), a root script (<name>.per), and optionally a folder of modules. The game finds it by name in the ai/ directory.
Why does the AI need it? Without the package structure the engine has nothing to load - a folder-only zip once caused a real "freezes on upload" incident because the load tree had no entry point.
What does the engine actually do? At match start the engine reads <name>.per and appends every (load "...") target, in order, into one rule table. A missing target breaks the load; order decides which definitions exist when later code is read. [Doc1 §2.2]
How do I write it? Smallest working example:
; LittleBot.per - the whole root for now
; (no loads yet: one file, no dependencies)
How do I know it worked? Create ai/LittleBot.ai (empty file) + ai/LittleBot.per with only the comment. Select LittleBot in a test match. The AI loads and does nothing - doing nothing, on purpose, is your first verified behavior.
What commonly goes wrong? Wrong folder, wrong basename (.ai vs .per mismatch), or saving as .txt. The AI will not appear or will not load.
Why did it go wrong, and how would a professional debug it? Checklist in order: files exist? basenames match? in ai/, not a subfolder? If the AI is absent from the dropdown, it is a file problem, never a code problem yet.
How does this connect to the previous lesson? None yet - this is the ground everything stands on.
Where does this lead next? Something the AI actually says.
Lesson 1.2 - First rule: chat on game start
What is this? A rule is one (defrule conditions => actions) block. Parentheses group; ; starts a comment; => separates "when" from "do".
Why does the AI need it? Rules are the only executable unit. Everything later - economy, armies - is rules plus state.
What does the engine actually do? Each pass the engine tests every rule top to bottom; rules whose conditions all hold execute their actions. A (true) condition always holds, so the rule fires every pass unless disabled. [Doc1 §5.1]
How do I write it? Smallest working example:
(defrule
	(true)
=>
	(chat-local-to-self "LittleBot lives.")
	(disable-self)
)
How do I know it worked? Launch with yourself observing that player (chat-local-to-self is local-only, white text, debug-grade [Doc1 §6]). You see the message exactly once. If it repeats forever, disable-self is missing - which teaches the next point.
What commonly goes wrong? Message repeats (no disable-self); message never shows (observing the wrong player); syntax error kills the whole file (one unbalanced paren disables everything, not just one rule).
Why did it go wrong, and how would a professional debug it? Classify first: repeats = scheduling/semantic; absent = symbol/load/parser. For parser suspicion, count parens per rule; the validator flags empty-fact/empty-action and defrule-missing-arrow.
How does this connect to the previous lesson? Lesson 1.1 gave you loading; this gives you execution. Together: load → evaluate → act.
Where does this lead next? Making the rule conditional on the world.
Lesson 1.3 - Facts: asking the engine questions
What is this? A fact is a named observation with a fixed shape, e.g. (game-time < 30), (current-age == dark-age), (food-amount >= 50). Facts do not change anything; they report.
Why does the AI need it? Conditions must come from what the engine can actually observe. You cannot test "am I winning" - you test countable proxies like populations and amounts.
What does the engine actually do? Facts evaluate against live engine state each pass. Some facts need acknowledgement side-protocols (taunt-detected stays true until acknowledge-taunt - unacknowledged, your response re-fires forever [Doc1 §6]).
How do I write it? Smallest working example:
(defrule
	(game-time > 10)
	(food-amount >= 50)
=>
	(chat-local-to-self "Ten seconds, food ok.")
	(disable-self)
)
How do I know it worked? Note the timestamp: message appears once, shortly after 0:10 game time. Change 10 to 60, reload, confirm the delay moves. You have now calibrated your observation loop.
What commonly goes wrong? Comparing incomparables (food-amount == dark-age); assuming a fact exists that does not (validator: unknown command); testing affordability with food-amount while escrow holds the food (foreshadows §Bot 3 escrow).
Why did it go wrong, and how would a professional debug it? Professional move: isolate one condition per test rule and log which one holds (up-chat-data-to-self with %d). Two conditions + one failure = ambiguity; one condition = diagnosis.
How does this connect to the previous lesson? Bot 1.2 fired blindly; now it fires on evidence. Next: remembering across passes.
Where does this lead next? Storing answers: goals.
Lesson 1.4 - Goals: the AI's private notebook
What is this? A goal is a named integer variable the script owns. (set-goal G const) writes; (goal G V) tests equality; (up-compare-goal G op V) compares against constants, goals (g:), or strategic numbers (s:). DE has 16,000 goals (UP: 512, AoC: 40). [Doc1 §3.2]
Why does the AI need it? Facts evaporate after the pass. Anything the AI must remember - "have I scouted?", "what plan am I on?" - lives in goals.
What does the engine actually do? The engine never writes your goals; only your rules do. Goals persist for the match and start at 0. Two writers on one goal need a convention (max-semantics or single owner) or they fight. [Doc1 §7.2]
How do I write it? Smallest working example:
(defconst my-plan 50)
(defrule
	(game-time > 10)
	(up-compare-goal my-plan == 0)
=>
	(set-goal my-plan 1)
	(chat-local-to-self "Plan set.")
)
How do I know it worked? Add a second rule that chats only when (goal my-plan 1). Observe order: first message, then second. Swap their source order and confirm nothing changes (different rules, no shared writes - order independence you will later lose).
What commonly goes wrong? CRITICAL, real-incident class: (set-goal R best) where best is a GOAL writes best's numeric ID (e.g. 3115), not its value - goal-to-goal copy is (up-modify-goal R g:= best) only. A whole regime machine once sat at invalid 3115 for this reason. [Doc1 §4]
Why did it go wrong, and how would a professional debug it? Suspect every set-goal whose second operand is not a plain number. The validator does not catch this - only reading the contract does.
How does this connect to the previous lesson? Facts observe the world; goals remember your conclusions. Next: numbers the engine itself owns.
Where does this lead next? Strategic numbers and prefixes.
Lesson 1.5 - Strategic numbers and the c:/g:/s: prefixes
What is this? Strategic numbers configure engine behavior (town size, gathering) and double as spare counters. Prefixes select the store an operand reads: c: constant, g: goal, s: strategic number. [Doc1 §4]
Why does the AI need it? Mixed expressions (goal vs SN vs literal) are everywhere in real bots; the prefix is the type system. Getting it wrong compiles and silently misbehaves.
What does the engine actually do? The engine substitutes defconst values at parse; g: reads goal RAM, s: reads the SN table. Same number, different stores - SN #213 and goal #213 are unrelated cells.
How do I write it? Smallest working example:
(defconst sn-max-vills 50)
(defrule
	(true)
=>
	(set-strategic-number sn-maximum-town-size 12)
	(disable-self)
)
How do I know it worked? Verify indirectly: town behavior changes are subtle, so instead log (up-chat-data-to-self "ts=%d" s: sn-maximum-town-size) in a second rule and read the value back. Round-trip proves the write landed.
What commonly goes wrong? REAL-INCIDENT class: (up-modify-goal bel g:max sn-ranged) reads GOAL #213 instead of SN #213 - validator-definite ("use s: when reading a strategic number value"). Symptom: the AI behaves "as if blind" to that input. Fix: s:max. [Doc1 §4]
Why did it go wrong, and how would a professional debug it? Any g: operand whose name starts with sn- is guilty until proven innocent. Search your files for it mechanically.
How does this connect to the previous lesson? You now own both stores. Next: doing things on a schedule instead of every pass.
Where does this lead next? Timers.
Lesson 1.6 - Timers: doing things on a schedule
What is this? A timer counts down game seconds. (enable-timer T N) starts it; (timer-triggered T) is true once it lapses; (up-timer-status T ...) inspects disabled/triggered/running (0/1/2). Timer ids run 1-50. [Doc1 §5.3]
Why does the AI need it? Per-pass rules are for cheap checks. Anything expensive or periodic (reassess strategy, log status) needs a heartbeat, or it burns the per-pass budget and spams.
What does the engine actually do? The engine counts enabled timers down in game seconds; triggered stays true until the timer is disabled or re-enabled. No automatic repeat exists - repetition is re-arming, done by your own rule.
How do I write it? Smallest working example:
(defconst one-minute 7)
(defrule
	(true)
=>
	(enable-timer one-minute 60)
	(disable-self)
)
(defrule
	(timer-triggered one-minute)
=>
	(chat-local-to-self "One minute.")
	(enable-timer one-minute 60)
)
How do I know it worked? Observe one message per game minute, repeatedly. Delete the re-arm line, reload, and observe exactly one message ever - a heartbeat silently becomes a one-shot. Restore it.
What commonly goes wrong? Missing re-arm (above); testing triggered without ever enabling (never fires); two rules enabling the same timer (ownership fight).
Why did it go wrong, and how would a professional debug it? If it fired once then stopped: timer problem, not condition problem. Check enable sites first.
How does this connect to the previous lesson? Bot 1 can now observe, remember, and schedule. Next: its first physical act - training a unit.
Where does this lead next? Production and verification.
Lesson 1.7 - First production: train + verify + fail on purpose
What is this? Production commands ((train U), (build B), (research T)) REQUEST engine action; guards ((can-train U), (can-build B), (can-research T)) test feasibility including resources and queue state. Request ≠ completion. [Doc1 §6]
Why does the AI need it? An AI that cannot convert resources into units is a spectator. This lesson also teaches the most important habit: verify physical completion, never assume it.
What does the engine actually do? train queues one unit if available and affordable WITHOUT escrowed stock; it checks the same criteria as can-train. Research without can-research guards is a documented crash risk - always guard. [Doc1 §6]
How do I write it? Smallest working example:
(defrule
	(unit-type-count-total villager < 6)
	(can-train villager)
=>
	(train villager)
)
How do I know it worked? Count villagers: TC produces until 6 total, then stops (the count condition goes false - completion observed in the world, not assumed). Now break it deliberately: remove can-train and watch nothing visibly change here-but note the contract: unguarded research/train is the documented crash class, so the guard stays forever.
What commonly goes wrong? Deliberate failures (do each, observe, revert): (a) drop a paren - whole file dead (parser); (b) misspell villager as vilager - rule dead (symbol); (c) remove the (load ...) after splitting files in 1.8 - rules missing (load); (d) use (goal ...) where up-compare-goal is needed - never true (semantic); (e) condition that can never hold, e.g. (game-time < 0) - silent (scheduling). Log each symptom.
Why did it go wrong, and how would a professional debug it? For each failure ask the taxonomy question from §0: parser, symbol, load, semantic, or scheduling? Write the symptom→class mapping in your notebook - it becomes Chapter "Debugging" later.
How does this connect to the previous lesson? Bot 1 is complete when it loads, chats, remembers, schedules, builds villagers to a counted target, and you have broken it five ways and classified each break.
Where does this lead next? Bot 2: coherence over time.
BOT 2 - THE THINKING BOT (coherent behavior over time)
Transition: from "do an action" to "maintain behavior". New machinery, one concept per lesson: state, transitions, guards, cooldowns, interruption, re-entry, ownership, production dials, recovery. [Doc1 §§5,7]
Lesson 2.1 - State: naming the situation
What is this? A state is a goal holding a situation id (e.g. my-mode: 0 opening, 1 harassed, 2 recovering), changed only by designated transition rules.
Why does the AI need it? Without named situations, every rule re-derives the world from scratch and different rules disagree mid-pass - incoherence.
What does the engine actually do? State persists until a rule rewrites it; nothing transitions automatically. Draw the graph on paper first: boxes, arrows, conditions on arrows.
How do I write it? Smallest working example:
(defconst my-mode 51)
(defrule
	(goal my-mode 0)
	(up-enemy-units-in-town > 0)
=>
	(set-goal my-mode 1)
	(chat-local-to-self "Harassed.")
)
How do I know it worked? Provoke: resign nothing - instead use a cheat-free trigger (send nothing; just wait for contact, or temporarily trigger on (game-time > 120)). Observe the single transition message. Then add the return arrow (town clear → 0) and watch it go back.
What commonly goes wrong? State with no exit (forgot the return arrow - dead state); two rules setting my-mode under overlapping conditions (competing writers - last in source order wins silently).
Why did it go wrong, and how would a professional debug it? Log the goal each minute (up-chat-data-to-self "mode=%d" g: my-mode). If it flickers 0/1/0, your enter and exit guards overlap - widen the gap (hysteresis: enter at >=2 enemies, exit at 0).
How does this connect to the previous lesson? Bot 1 goals stored facts; Bot 2 goals store situations. Next: guarding the arrows.
Where does this lead next? Transition guards and dead states.
Lesson 2.2 - Guards, dead states, unreachable states
What is this? A guard is the full condition on a transition arrow. A dead state has no exit arrow; an unreachable state has no entry arrow. Audit every box for both.
Why does the AI need it? Most "frozen AI" reports are dead states, not crashes: the machine sits somewhere legal with nowhere to go.
What does the engine actually do? Nothing in the engine detects dead states. Your minute-log from 2.1 is the detector.
How do I write it? Smallest working example:
; INTENTIONALLY BROKEN: entry arrow only, no exit
(defrule
	(goal my-mode 0)
	(up-enemy-units-in-town > 0)
=>
	(set-goal my-mode 1)
)
How do I know it worked? Take your 2.1 machine; intentionally delete the return arrow. Observe: mode sticks at 1 forever after first contact. Restore it. You have now seen, on purpose, the most common real-bot pathology.
What commonly goes wrong? Accidental loops (A→B→A in one pass via cascading rules); transitions firing too early (guard too weak) or never (guard too strong).
Why did it go wrong, and how would a professional debug it? For a stuck machine: log state + each guard's inputs for three ticks. The guard that should hold but does not names the broken assumption.
How does this connect to the previous lesson? Machines need clocks next: cooldowns.
Where does this lead next? Cooldowns and re-entry.
Lesson 2.3 - Cooldowns, interruption, re-entry
What is this? A cooldown is a timer that forbids re-entry until it lapses. An interruption is a high-priority transition out of a durable activity; re-entry resumes it with saved context instead of restarting. [Doc1 §7.3]
Why does the AI need it? Fixed sequences fail when the world changes mid-sequence (attack ordered, town then raided). Without interrupt+resume the AI either feeds units or stands down entirely.
What does the engine actually do? Timers count game seconds; retreat/attack orders execute over many passes. Shadow sequences tech pauses with a pause enum + release (pause ≠ −1 suspends, −1 resumes) - interruption with explicit resume state, not amnesia. [Doc1 §7.1]
How do I write it? Smallest working example:
Build: attacking-goal + retreat-timer 16. Rule A: emergency + army → groups-zero + up-retreat-now + enable retreat-timer (do NOT cancel the attack authorization). Rule B: while retreat-timer runs, deny new attacks. Rule C: on expiry, normal logic resumes. Log each transition.
How do I know it worked? Verify with the transition log: provoke an emergency with an army fielded - observe retreat ordered while attack authorization stays set, zero new attacks while the timer runs, and normal logic resuming on expiry. Three log lines in order = working interruption.
What commonly goes wrong? Canceling authorization instead of pausing execution (forces full stand-down + slow re-authorization - the passivity ratchet); resuming into an obsolete objective (restore must re-check guards, not blindly continue).
Why did it go wrong, and how would a professional debug it? If post-retreat behavior looks drunk: check whether resume re-evaluated guards (correct) or replayed a stale order (bug). The retreat-timer status line in your log answers it.
How does this connect to the previous lesson? Interruption needs owners: who may cancel whom.
Where does this lead next? Ownership and competing writers.
Lesson 2.4 - Ownership: one writer per state
What is this? Ownership = exactly one rule-family may write a goal; everyone else reads. Competing writers = two families writing one goal with different intents.
Why does the AI need it? Silent fights produce flicker (values oscillating per pass) and "works until the other subsystem loads" regressions.
What does the engine actually do? Source order decides last-writer-wins within a pass - deterministic but invisible. That is why ownership is a design rule, not an engine rule.
How do I write it? Smallest working example:
Exercise: create two rules writing one goal differently; observe flicker in the log. Then fix by ownership: family A writes desire-A, family B writes desire-B, one arbiter rule writes the real goal as max(A,B). You have built your first arbiter.
How do I know it worked? Verify: the flicker demo shows oscillation in the log; after the arbiter fix, the log shows a stable max value from a single writer. One writer per goal, proven by a flat line.
What commonly goes wrong? Two families writing one goal with different intents (flicker); "tuning the timing" instead of arbitrating (never works); one writer raising what another lowers (ownership violation).
Why did it go wrong, and how would a professional debug it? Flicker in a log + two writers found = ownership bug. Merge or arbitrate; never "tune the timing". Naga's train dials are the reference pattern for conflict-free sharing: many writers raise ceilings with c:max (never lower), one producer family reads. [Doc1 §7.2]
How does this connect to the previous lesson? Owned state is what production dials consume - desire without fights.
Where does this lead next? The production dial.
Lesson 2.5 - The production dial (desire vs execution)
What is this? A dial is a goal holding "how many of X I want" (ceiling). Desire rules raise it (c:max only); producer rules compare (unit-type-count-total X g:< dial) + can-train, then train. Decrement on escrow spend. [Doc1 §7.2, Naga units.per:1336-1351 → 11323-11329]
Why does the AI need it? Desire and feasibility change on different timescales (threats spike fast; buildings/queues clear slowly). The dial decouples them so spikes do not stampede the queue.
What does the engine actually do? train is a queue request checked like can-train; escrowed stock is invisible to it - escrow spends need can-train-with-escrow + dial decrement (Naga escrow.per:635-640).
How do I write it? Smallest working example:
(defrule
	(strategic-number sn-cavalry >= 3)
=>
	(up-modify-goal train-spear g:max 4)
)
(defrule
	(unit-type-count-total spearman-line g:< train-spear)
	(can-train spearman-line)
=>
	(train spearman-line)
)
How do I know it worked? Spawn enemy cavalry (scenario or cheat-free raid); observe dial rise in logs then spears queueing. Remove the threat; dial stays (no lowering rule) - observe overproduction, then add expiry. You have felt why memory/expiry exists (Bot 3).
What commonly goes wrong? Dial never read (producer missing - desire without executor); dial lowered by a second writer (ownership); escrow spend without decrement (dial stuck high).
Why did it go wrong, and how would a professional debug it? Dial high + count low + no queue = producer/feasibility problem. Dial low + threat high = desire problem. The split tells you which half to open.
How does this connect to the previous lesson? Production needs resources with honest accounting.
Where does this lead next? Recovery: expected vs observed.
Lesson 2.6 - Recovery: closing the loop
What is this? Recovery = EXPECTED (requirement) vs OBSERVED (counts) → divergence deficit → correction → restoration → reassessment. Deficit = max(desire...) − current, floored at 0. [Doc1 §7.6]
Why does the AI need it? Open-loop bots (request without verification) rot: queued units die, buildings never place, the plan assumes success that never happened.
What does the engine actually do? Completion is observed in the world (counts changed, building exists), never inferred from issuing the command.
How do I write it? Smallest working example:
Add a deficit goal: desire − count each minute; if deficit persists 3 ticks, log "UNMET: <x>" and try the alternate producer (different building). Watch a supply-blocked queue get diagnosed by your own rule.
How do I know it worked? Verify: block supply deliberately (queue to cap) and watch your own rule print UNMET naming the right producer; unblock and watch the deficit drain to 0. Detector fires and clears = loop closed.
What commonly goes wrong? Assuming the queue drains (it does not under supply block); retrying the same blocked producer forever (needs blocked-flags: building absent → demand unfillable, stop spending arbitration on it).
Why did it go wrong, and how would a professional debug it? Persistent UNMET + building absent = infrastructure gap (expand production), not a dial problem. The flag, not the feeling, decides.
How does this connect to the previous lesson? Bot 2 ends with a bot that holds situations, interrupts cleanly, produces through dials, and diagnoses its own shortfalls.
Where does this lead next? Bot 3: adapting to an enemy.
BOT 3 - THE ADAPTIVE BOT (observe → verify)
Decomposition, built one arrow at a time: WORLD → OBSERVATION → CLASSIFICATION → CAPABILITY MODEL → REQUIREMENT → CANDIDATE RESPONSE → RESOURCE CONSEQUENCE → AUTHORITY → EXECUTION → WORLD-STATE RESULT → VERIFICATION → REASSESSMENT. Observing is not classifying; classifying is not authorizing; issuing is not proof. [Doc1 §7]
Lesson 3.1 - Observation: latching a volatile world
What is this? Engine threat inputs (e.g. per-pass census SNs) reset constantly - Naga zeroes its threat SNs every pass (threats.per:412-431). A latch copies a sighting into a goal + timestamp so absence-of-sighting ≠ absence-of-threat.
Why does the AI need it? Without latching, LOS flicker becomes threat flicker becomes production flicker.
What does the engine actually do? SEEN (SN>0 → goal + game-time stamp) → CURRENT (fresh) → STALE (retained, no new surge) → EXPIRED (release to 0). Time constants ride existing cadences (60 s scoring tick).
How do I write it? Smallest working example:
(defrule
	(strategic-number sn-cavalry > 0)
=>
	(up-modify-goal bel-cav s:= sn-cavalry)
	(up-get-fact game-time 0 seen-cav)
)
How do I know it worked? Raid with cavalry, withdraw, watch bel-cav persist after sn-cavalry returns to 0. Then confirm expiry releases it. Both halves must be observed.
What commonly goes wrong? The s:/g: store confusion (Bot 1.5, real incident) - latched garbage here poisons every downstream layer. Verify latch values equal the SN at sighting time.
Why did it go wrong, and how would a professional debug it? Mismatch at sighting = prefix/store bug. Match at sighting but no persistence = timestamp/expiry bug. Split accordingly.
How does this connect to the previous lesson? Latched beliefs feed classification.
Where does this lead next? Classification → requirement.
Lesson 3.2 - Classification, capability gap, requirement
What is this? Classification maps sightings to threat classes; capability gap = believed threat − fielded answer; requirement = the count that closes it. Standing (age-based minima) persists after beliefs expire - counter-fulfilled ≠ army-fulfilled.
Why does the AI need it? Threat-gone must release the counter without disbanding the army; otherwise success causes stagnation, then collapse at the next wave.
What does the engine actually do? Joint requirement = max(belief, standing, dial): expiry releases counters, standing sustains Cases A/D. Funding gates only discretionary top-up, never mandatory counters.
How do I write it? Smallest working example:
Implement one line end-to-end: bel-cav + stand + train-camel → deficit → producer. Test both release (threat leaves → counter releases, standing remains) and sustain (no threat, standing still fields camels).
How do I know it worked? Verify both halves in the log: threat present → deficit above 0 and camels queue; threat withdrawn → counter releases to the standing floor (not to 0 while standing holds); standing alone with no threat still fields the floor.
What commonly goes wrong? Belief without standing (stagnation after expiry); standing without funding gate (gold core starved by trash top-up); shared ceiling ignored (two needs overspend - needs arbitration).
Why did it go wrong, and how would a professional debug it? Counter released but army gone too = standing bug. Army present but counter never released = expiry bug. Funded dual-threat = correct immunity, not a bug.
How does this connect to the previous lesson? Requirements compete for gold next.
Where does this lead next? Resource consequence and escrow.
Lesson 3.3 - Escrow: honest resource accounting
What is this? Escrow is a second stockpile: set-escrow-percentage diverts income, can-X-with-escrow spends it, release-escrow returns it. Gross-amount checks cannot see it; normal commands cannot spend it. Shadow mirrors physical escrow into goals and reasons on NET = gross − escrowed (Shadow DC7.per:1821-1845). [Doc1 §7.1]
Why does the AI need it? Age-ups and techs need lump sums to survive contact with per-pass spenders. Unprotected savings get eaten by trash floods one villager at a time.
What does the engine actually do? Research with escrow: collect (up-modify-escrow c:max N under a pause id) → fire (can-research-with-escrow → up-research + release + pause −1). Castle Age via escrow with a build-item gate (Shadow DC7.per:14893-14905).
How do I write it? Smallest working example:
Save for Castle: escrow food/gold percentages up while (food < 800); at can-research-with-escrow castle-age, release + research. Observe the stockpile curve bend then jump - then observe a trash rule eating it when you forget the escrow guard on discretionary top-up.
How do I know it worked? Verify the savings curve: stockpile climbs while percentages hold, research fires exactly at can-research-with-escrow, escrow returns to 0 after release. Then verify the failure mode: remove one producer guard and watch the curve flatten - the guard's value, demonstrated.
What commonly goes wrong? Gross-check misfire (checking food-amount while escrow holds it); un-released escrow starving normal production; pause never cleared (−1 discipline).
Why did it go wrong, and how would a professional debug it? Savings never arrive = producers eating them (add guards) or percentages never set (authority bug). Research fires but queue was busy = preconditions, not resources.
How does this connect to the previous lesson? Funded requirements need an executor with a trigger.
Where does this lead next? Authority: superiority-gated attack.
Lesson 3.4 - Attack authority and verification
What is this? Attack authority = the named bit + preconditions that start/stop violence. Naga: attacking goal + sn-military-superiority bands (start sup ≥ 0-2 with mass/age/tech context at militaryMacro.per:730-745; assisted bar sup ≥ −1 at 746-757; retreat at ≤ −1/−2). Shadow: gl-attacking + town-size 1000 + TSA timer, retracted symmetrically. [Doc1 §7.5]
Why does the AI need it? Starting fights is easy; stopping bad ones and not oscillating is the skill. Dual authorities without precedence flicker attack↔retreat every pass.
What does the engine actually do? Verification closes every loop: after execution, observe counts/positions, recompute the gap, reassess. Unverified commands are assumptions with side effects.
How do I write it? Smallest working example:
Implement: sup ≥ 1 + mass → set attacking; sup ≤ −2 in field → groups-zero + retreat (keep authorization); E2 town emergency → groups-zero + retreat-now + edge latch. Log every transition. Then break it: remove timer guards, watch oscillation, restore.
How do I know it worked? Verify in one match: attack starts only at superiority with mass (log line), field disadvantage triggers retreat without canceling authorization, town emergency triggers the edge latch exactly once. Remove timer guards, observe oscillation, restore - that oscillation log is your regression test.
